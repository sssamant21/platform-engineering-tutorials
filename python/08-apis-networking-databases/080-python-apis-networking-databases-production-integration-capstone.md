# Chapter 080 — Python APIs, Networking and Databases Production Integration Capstone

**Part 08 — APIs, Networking and Databases | Chapter 080 of 120 | SRE/DBRE Capstone**

## Mission
Build a reliable ingestion service that collects operational metrics from a secured HTTP endpoint, concurrently polls multiple services with bounded concurrency, validates and deduplicates observations, persists them through SQLAlchemy transactions, and exposes an auditable checkpoint. Rehearse PostgreSQL connectivity with psycopg 3, version the schema with Alembic, export results in bounded batches, instrument failures and recover safely from partial outages.

**Production acceptance is not the same as publishing code.** The companion lab supplies an executable SQLite default profile with loopback HTTP fixtures and optional disposable PostgreSQL integration. External production endpoints and databases are never contacted by default.

## Learning outcomes
1. Separate transport errors from HTTP 429/5xx and permanent 4xx failures.
2. Use \`asyncio.Semaphore\` and \`httpx.AsyncClient\` without unbounded fan-out.
3. Keep bearer tokens out of logs and require TLS verification for remote endpoints.
4. Apply JSON schema-like validation before SQL writes.
5. Calculate stable idempotency keys across retries; never assume a timeout means no commit.
6. Use SQLAlchemy transactions, bind parameters and explicit connection pool limits.
7. Version the schema with Alembic; test upgrade and downgrade on disposable data.
8. Compare SQLite smoke behavior with PostgreSQL/psycopg 3 semantics.
9. Export records in bounded chunks and plan server-side PostgreSQL cursors for larger datasets.
10. Emit structured operational metrics without leaking secrets or payloads.
11. Diagnose DNS, TLS, connection, pool, lock, statement and job deadline failures separately.
12. Produce an operational acceptance score and rollback decision.

## 1. HTTP client and concurrency
Use one reusable \`httpx.AsyncClient\` per batch, with explicit connect/read/write/pool timeouts and finite connection limits. \`asyncio.Semaphore\` caps in-flight requests. Retry only transient transport failures and explicit 429/502/503/504 responses, with bounded exponential backoff and a small jitter. Respect \`Retry-After\` only after validating it and enforcing a maximum wait; do not allow arbitrary server delays to exceed the job deadline. An HTTP 401/403 is an authentication/authorization incident, not a retry signal. For production, integrate circuit breaking and a bounded input queue.

## 2. Secure networking
The executable fixture is restricted to \`http://127.0.0.1\` on ephemeral ports and uses a synthetic bearer token. Production requires \`https://\`, certificate-chain and hostname verification, approved CA roots, secret rotation, egress allowlists, DNS controls, audit logging and network policy. Do not use \`verify=False\` or log authorization headers. A valid TLS handshake does not prove application identity or authorization.

## 3. Database and transactions
The default integration uses SQLite with SQLAlchemy \`QueuePool\` for deterministic local tests. Production PostgreSQL uses the \`postgresql+psycopg\` dialect with finite \`pool_size\`, \`max_overflow\`, \`pool_timeout\`, \`pool_pre_ping\` and \`connect_timeout\`. Budget total connections as replicas × processes × (pool_size + max_overflow), including rollout overlap. Transaction boundaries encompass idempotency check and insert. Prefer PostgreSQL \`INSERT ... ON CONFLICT\` for atomic deduplication under concurrency; an application-level SELECT-then-INSERT is race-prone. Retry SQLSTATE 40001/40P01 only by replaying the entire safe transaction with a bounded budget; reconcile ambiguous commits.

## 4. Schema lifecycle
Use Alembic \`revision\`, \`upgrade\`, \`current\` and \`downgrade\` on a disposable database. Apply expand–backfill–cutover–contract across releases. Treat autogenerated diffs as drafts requiring review. A downgrade that drops a table destroys data and must never be used as a default production rollback. Concurrent migration runners must be prevented by deployment orchestration.

## 5. Batching and streaming
Ingest small, bounded groups with clear commit boundaries. The capstone's default export iterates ordered rows with a fixed \`LIMIT\` and keyset cursor; this avoids unbounded \`fetchall\`. For large PostgreSQL reports, named server-side psycopg cursors allow incremental fetching but hold a transaction snapshot; bound cursor lifetime and consider checkpointed keyset pagination for long jobs. \`COPY\` can improve bulk load throughput but requires WAL/replication monitoring and reconciliation.

## 6. Observability and SLOs
Collect counters for attempted/succeeded/failed polls, HTTP status classes, retries, validation failures, database write outcomes and duplicates. Record request duration, pool checkout wait, SQL latency, batch size, transaction age and backlog. Correlate with PostgreSQL \`pg_stat_activity\`, lock waits, WAL/replica lag and application logs. Never log token values, raw credentials or PII. Suggested acceptance targets are **exercise targets**, not universally appropriate production SLOs: 100% idempotent replay, zero secrets in logs, zero unbounded queues, successful controlled rollback, and all mandatory tests passing.

## 7. Failure matrix
| Failure | Signal | Containment |
|---|---|---|
| DNS resolution | \`gaierror\` / transport exception | Verify resolver; bounded retry only |
| TLS certificate | verification error | Restore trust/hostname; never bypass |
| HTTP 429 | rate limited | bounded retry/backoff |
| HTTP 503 | upstream outage | shed load, cap retries |
| HTTP 401 | token invalid | rotate credentials; no retry storm |
| Bad JSON | decode/validation failure | quarantine/reject payload |
| Duplicate event | unique constraint | idempotent no-op |
| Pool exhausted | SQLAlchemy QueuePool timeout | bound workers, inspect leaked connections |
| PostgreSQL 40001 | serialization conflict | whole safe transaction retry |
| PostgreSQL 40P01 | deadlock | lock order, bounded retry |
| COMMIT response lost | ambiguous outcome | reconcile by event key |
| Migration blocked | \`pg_locks\` wait | stop runners, inspect blockers |
| Replica lag | replay delay | throttle ingest/COPY |
| Memory growth | unbounded result materialization | keyset/stream batches |

## 9. Operational runbooks
**API degradation:** inspect HTTP error classes and concurrency, confirm upstream rate limits, reduce fan-out, disable unsafe retries, verify token/TLS and run synthetic canary.

**Database pool exhaustion:** inspect checked-out connections and active transactions, calculate aggregate pool budget, cap concurrency, repair leaks and validate p95 latency.

**Duplicate or uncertain writes:** use immutable event key to reconcile database state; do not blindly replay after ambiguous COMMIT.

**Migration failure:** stop parallel runners, inspect revision/locks and schema drift, favor compatible application rollback or forward-fix; restore from backup only through approved DR procedure.

**Data export pressure:** reduce batch size, checkpoint by primary key, monitor RSS and long transactions, pause if replica lag or WAL exceeds thresholds.

**Incident closure:** rerun tests, compare SLO baselines, verify no secret leakage, attach change/rollback evidence and identify owners.
