## Learning outcomes

Design and operate a defensible Python software supply chain: trusted source, reproducible dependency resolution, SBOM generation, vulnerability and license risk review, artifact signing and provenance, SLSA-aligned build controls, hardened GitHub Actions/CI/CD, promotion gates and incident response. Implement a safe offline dependency/SBOM **teaching simulator**, not a live vulnerability scanner or signature verifier.

## Architecture

```text
Reviewed source + protected branches + signed reviews

                         |
```

## 1. Threat modeling the Python supply chain

Threats include dependency confusion, typosquatting, malicious maintainers, compromised package indexes, poisoned build runners, stolen CI credentials, malicious pull requests, workflow injection, tampered artifacts and unreviewed transitive dependencies. Assess build-time code execution: `pip` installs and source builds can run untrusted code. Treat dependency installation as privileged execution and isolate it.

Separate source trust, build trust, artifact integrity, vulnerability status and deployment authorization. A hash match proves bytes match an independently trusted digest; it does **not** prove the bytes are safe or authored by a trusted party.

## 2. Python packaging and dependency pinning

Use isolated virtual environments, trusted indexes, explicit versions and hashes, reviewed lockfiles and `pip install --require-hashes` with hashes for **all** installed transitive dependencies. Lock across supported Python versions/platforms or generate environment-specific locks. Avoid mutable `latest`, unreviewed direct URLs and dependency-confusion fallbacks to public indexes. Prefer wheels from reviewed sources, with build isolation and offline wheelhouses when appropriate.

```bash
python -m venv .venv
python -m pip install --upgrade pip
# After generating and reviewing a fully hashed requirements lock:
python -m pip install --require-hashes -r requirements.lock
```

These commands are **production-design examples**, not executed by the offline simulator.

## 3. SBOM: CycloneDX and SPDX

An SBOM inventories direct and transitive components, versions, package URLs, hashes, licenses and dependency relationships. CycloneDX and SPDX are standardized formats with schemas and tooling. Generate an SBOM from the resolved build environment/artifact, validate it against the chosen standard, and publish alongside artifact digest and build identity.

The executable lab emits an explicitly labeled **educational JSON inventory, not valid CycloneDX or SPDX**. Its hashes are synthetic examples and must not be used as real package digests.

## 4. Vulnerability scanning and risk triage

Use maintained tools such as `pip-audit`, OSV-Scanner, Dependabot, GitHub code/dependency scanning or an approved enterprise service. Scan direct/transitive dependencies, base images, container layers and CI actions. Interpret CVEs/GHSAs/OSV advisories with version ranges, fix availability, exploitability, deployment exposure and reachability. Do not equate no scanner matches with absence of vulnerabilities. Track feed freshness, false positives, exceptions and SLAs.

```bash
python -m pip_audit --requirement requirements.lock
# Or use an approved OSV-Scanner workflow with reviewed configuration
```

The lab uses a **synthetic advisory feed**, not real vulnerability intelligence or CVE validation.

## 5. SLSA and build provenance

SLSA provides a framework for increasing software supply-chain assurance through source/build requirements and provenance. Record builder identity, source repository and immutable commit, build parameters, dependencies, artifact digest and build environment. Select the applicable SLSA version and level based on verifiable controls; do not claim a level from a single JSON field.

Provenance should be generated by a trusted build system and cryptographically authenticated, not self-asserted by an untrusted build script.

## 6. Artifact signing and verification

Use reviewed signing solutions such as Sigstore/cosign with keyless OIDC identity or managed signing keys. Verify signature, trusted issuer/identity, artifact digest, transparency log/bundle as applicable and expected provenance policy before promotion. Understand trust roots, certificate validity, offline verification and key rotation. Do not confuse a SHA-256 fingerprint with a digital signature.

The simulator only compares SHA-256 of local byte strings against a supplied expected digest. It **does not sign or cryptographically verify software provenance**.

## 7. GitHub Actions and CI/CD hardening

Use `permissions: contents: read` by default, grant `id-token: write` only to specific OIDC federation jobs, pin third-party actions by reviewed full commit SHA, isolate untrusted pull requests from secrets and write tokens, protect environments, require reviews and avoid injecting attacker-controlled strings into shell scripts. Restrict runner egress, ephemeral runner credentials and artifact retention.

Avoid privileged `pull_request_target` checkout of untrusted code. Use trusted artifact promotion and immutable image digests in GitOps. Store secrets in approved vaults and use cloud workload identity instead of static keys.

## 8. Dependency risk and change approval

Track dependency owner, criticality, vulnerability severity, exploitability, affected service, remediation version, change ticket, exception expiry and rollback. Require independent approval for critical exceptions or production releases. Bind approval to immutable commit, artifact digest, SBOM digest and ticket. The offline simulator produces advisory decisions only; no CI, package installation or deployment is performed.

## 9. SRE/DBRE incidents and runbooks

| Incident | Safe response |
|---|---|
| Malicious package release | Quarantine builds, revoke tokens, inspect installs and rebuild from trusted source |
| Dependency confusion | Restrict indexes, namespace ownership and reviewed locks |
| Compromised GitHub Action | Disable workflow, rotate credentials, audit run artifacts |
| Missing SBOM | Block promotion and regenerate from trusted artifact |
| Critical vulnerability | Validate reachability, exposure, fix and emergency mitigation |
| Artifact digest mismatch | Quarantine artifact, verify trusted provenance |
| Signing identity mismatch | Stop deployment, inspect OIDC trust policy |
| CI runner compromise | Revoke credentials, isolate runner and rebuild |
| Stale vulnerability feed | Mark assessment unknown and refresh feed |
| Database migration dependency risk | Stage, test rollback and protect backups |

**Runbook — compromised dependency:** identify affected lockfiles/builds, quarantine registry artifacts, review SBOM and runtime exposure, rotate compromised credentials, rebuild and redeploy with verified provenance.

**Runbook — provenance failure:** stop promotion, inspect builder identity, issuer, artifact digest, source commit, attestation and trust roots.

**Runbook — critical CVE:** evaluate affected versions, exploitability, reachable code, mitigation and SLO risk; patch, test and stage with rollback.

**Runbook — CI compromise:** freeze deployment, preserve logs, rotate runner/OIDC credentials, audit artifact registry and re-establish trusted build.

**Runbook — DBRE release rollback:** verify schema compatibility, backup/RPO, connection pools, migrations and observability before rollback.
