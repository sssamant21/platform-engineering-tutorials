# Chapter 023 — Container Image Signing, Provenance Attestations and SLSA Supply-Chain Controls

**Part 05 — Container Builds and Software Supply-Chain Security** | **Chapter 023 / 100**  
**Audience:** SRE, infrastructure, platform, DevSecOps and release engineers  
**Lab:** Disposable OCI registry, Cosign, a test image digest, a local test signing key, GitLab CI validation  
**Production pattern:** Trusted GitLab CI builds once, signs and attests the exact published digest; reviewed GitOps promotion reuses that digest through \`demo-dev\`, \`demo-test\`, \`demo-staging\`, and \`demo-prod\`.

## 2. Trust architecture

\`\`\`text
Developer MR
  |
  +--> tests / SAST / dependency and secret scans
  |      untrusted runner; NO signing credentials
  |
Protected main after approval
  |
  v
Trusted isolated build runner
  |
  +--> reviewed source commit
  +--> controlled builder and dependencies
  +--> build once and publish OCI image
  |                  |
  |                  v
  |           registry image@sha256:...
  |                  |
  +--> SBOM ---------+
  +--> provenance ---+--> trusted signer
                            |
                            +--> image signature
                            +--> signed attestations
                                      |
                             verify signer + digest
                                      |
                             reviewed GitOps MR
                                      |
                                Argo CD sync
                                      |
                   demo-dev -> demo-test -> demo-staging -> demo-prod
\`\`\`

A signature says a signer approved particular bytes. It does **not** prove the application is secure, the source was reviewed, or the build environment was trustworthy. Provenance provides claims about how an artifact was built; its value depends on the credibility and isolation of the builder and signing identity.

## 3. Essential concepts

| Concept | Meaning | SRE check |
| --- | --- | --- |
| Image digest | Content-addressed OCI manifest or index | Match exact deployed reference |
| Signature | Cryptographic binding between signer and artifact | Verify trusted signer and target digest |
| SBOM | Inventory of included components | Check format, coverage, artifact binding |
| Attestation | Signed statement about an artifact | Verify predicate type and subject |
| Provenance | Evidence about source, builder, inputs and invocation | Confirm trustworthy build origin |
| SLSA | Supply-chain assurance framework | Assess actual build controls, not just labels |
| Keyless signing | Signing identity established through OIDC and certificate issuance | Restrict issuer, identity and transparency verification |
| Admission control | Policy at Kubernetes deployment boundary | Reject untrusted or unsigned artifacts |

**Do not confuse:** a self-authored JSON provenance file with independently generated builder provenance. The lab deliberately uses **self-declared training provenance**, which must not be represented as SLSA-compliant production evidence.

## 4. SLSA in operational terms

SLSA focuses on increasing confidence that an artifact came from the intended source and trusted build process. Evaluate controls such as:

- Trusted and authenticated source repository/ref.
- Builder isolation from untrusted projects and jobs.
- Provenance generated by the build service, not arbitrary application code.
- Non-forgeable linkage between source, build and artifact digest.
- Protected signing identity and tamper-resistant evidence storage.
- Repeatable verification by consumers and deployment policy.

SLSA terminology and level requirements depend on the framework version. Record the SLSA specification version in assessments; do not claim a level based solely on signing an image or writing a provenance JSON file.

## 6. Lab A — Generate a disposable signing identity

Create a temporary directory with restricted permissions:

\`\`\`bash
mkdir -p "$HOME/ch023-signing"
chmod 700 "$HOME/ch023-signing"
cd "$HOME/ch023-signing"
cosign generate-key-pair
\`\`\`

Cosign prompts for a password and generates \`cosign.key\` and \`cosign.pub\` for this **lab only**. Never put the private key in Git, a container image, CI artifacts or logs.

For PowerShell, create a separate folder under your user profile, run \`cosign generate-key-pair\` there, and apply appropriate Windows filesystem ACLs. Do not rely on \`chmod\` in PowerShell.

**Production:** Prefer a supported keyless OIDC flow or a protected KMS/HSM signing key, with identity policy and audited access. Local key files are useful for learning but inappropriate for shared production signing.

## 7. Lab B — Sign an actual image digest

Set values to the **real** registry repository and digest from Chapter 021:

\`\`\`bash
export IMAGE_REPO="registry.example.com/training/demo-app"
export IMAGE_DIGEST="sha256:<REPLACE_WITH_REAL_DIGEST>"
export IMAGE_REF="$IMAGE_REPO@$IMAGE_DIGEST"
\`\`\`

Confirm that the reference resolves:

\`\`\`bash
docker buildx imagetools inspect "$IMAGE_REF"
\`\`\`

Sign the exact digest:

\`\`\`bash
cosign sign --key ./cosign.key --yes "$IMAGE_REF"
\`\`\`

Verify using the corresponding public key:

\`\`\`bash
cosign verify --key ./cosign.pub "$IMAGE_REF"
\`\`\`

Expected: verification succeeds and reports a signature associated with the exact digest. Do not hardcode an expected signature count; registries can contain multiple signatures.

**Security control:** Verification with a public key proves the signature corresponds to its private key, not that the key is trusted. In production, pin the approved public key or signer identity through independently governed policy.

## 8. Lab C — Create a signed provenance attestation

Create \`training-provenance.json\`:

\`\`\`json
{
  "buildType": "https://example.com/training/manual-build/v1",
  "builder": {
    "id": "https://example.com/training/local-builder"
  },
  "invocation": {
    "parameters": {
      "pipeline": "manual-training"
    }
  },
  "metadata": {
    "completeness": {
      "parameters": false,
      "environment": false,
      "materials": false
    },
    "reproducible": false
  },
  "materials": []
}
\`\`\`

This is an intentionally minimal, **self-declared training predicate**, not verified SLSA provenance. It does not establish source commit, trusted builder or complete inputs.

Attach it to the actual image digest using a named predicate type supported by your Cosign version:

\`\`\`bash
cosign attest --yes --key ./cosign.key \
  --type https://example.com/training/provenance/v1 \
  --predicate training-provenance.json \
  "$IMAGE_REF"
\`\`\`

Verify the signed attestation:

\`\`\`bash
cosign verify-attestation --key ./cosign.pub \
  --type https://example.com/training/provenance/v1 \
  "$IMAGE_REF"
\`\`\`

**Version caveat:** Some Cosign versions enforce specific predicate type names, accepted payload schemas or alternative OCI storage formats. If this command is rejected, inspect \`cosign attest --help\` and use a supported custom predicate type/format; record the deviation rather than claiming the lab succeeded. Do not mislabel the self-declared payload as a standard SLSA predicate.

### Evidence to inspect

- The attestation's subject matches the exact image digest.
- The predicate type is the training type, not a false claim of production SLSA provenance.
- The verification succeeds with the approved public key.
- The payload and public key are recorded separately from the private key.

## 9. Lab D — Negative verification tests

### Test 1 — Wrong public key

Create a second disposable key pair in another directory and attempt verification with its public key.

\`\`\`bash
mkdir -p other-key
cd other-key
cosign generate-key-pair
cd ..
cosign verify --key ./other-key/cosign.pub "$IMAGE_REF"
\`\`\`

Expected: verification fails because the image was not signed by the second key. Do not treat a verification failure as a scanner or registry availability failure without examining the error.

### Test 2 — Unsigned image

Build and push a second disposable image under a different digest, without signing it, then attempt \`cosign verify\` with the original public key.

Expected: verification fails. Use an isolated training repository; avoid accidentally testing an image signed by another authorized process.

### Test 3 — Tampered provenance

Edit a local copy of \`training-provenance.json\` **after** attestation publication. This does not change the signed registry attestation. Compare the modified file with the verified registry payload.

Expected: the local edited file is not evidence of what was signed. If an attestation payload were altered in transit without a new valid signature, cryptographic verification would fail.

### Test 4 — Digest mismatch

Attempt verification for a different valid training digest using the original signature policy.

Expected: a signature for digest A does not authorize digest B.

### Test 5 — Revoked signing authority

Document how the trusted public key or signer identity would be removed from deployment verification policy. Do not delete or alter production signing keys during the lab.

Expected: an otherwise cryptographically valid signature is no longer accepted when its signer is no longer trusted.

## 10. GitLab CI trust separation

| Pipeline | Runner trust | Permitted actions |
| --- | --- | --- |
| MR validation | Untrusted isolated runner | Unit tests, SAST, dependency checks |
| Protected build | Trusted isolated builder | Build and publish exact digest |
| Signing | Restricted signer identity | Sign only approved digest |
| Verification | Read-only identity | Verify digest, signer and attestation |
| GitOps promotion | Approved automation | Propose digest change through MR |
| Kubernetes admission | Cluster policy | Reject images that violate trust rules |

Never expose signing keys or privileged OIDC identity tokens to contributor-controlled MR jobs. Protected branches, approval rules and centrally governed CI configuration must prevent contributors from changing signing policy.

### Illustrative signing job

\`\`\`yaml
# REFERENCE ONLY: requires a supported trusted runner, protected
# variables, approved Cosign image and a previously published digest.
sign_published_image:
  stage: sign
  tags: [trusted-signing]
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: on_success
    - when: never
  script:
    - test -n "$PUBLISHED_IMAGE_DIGEST"
    - echo "Signing must use approved keyless/KMS workflow"
    - exit 1
\`\`\`

This deliberately **fails closed** rather than pretending that an echo command signs an image. Replace it with a reviewed, version-specific signing integration that receives the digest from a trusted build job and enforces the signing identity's scope.

### Required release gates

1. All mandatory validation jobs pass.
2. Trusted build publishes one digest.
3. Scanner and SBOM reports correspond to that digest.
4. Signature verification identifies an approved signer.
5. Provenance identifies an approved builder and source.
6. GitOps MR changes only the intended image digest.
7. Production promotion requires approval and post-deployment health checks.

## 11. Keyless signing and OIDC

Keyless signing typically uses a workload identity token issued to a CI job, a certificate authority, and a transparency mechanism where supported. It avoids long-lived private keys in CI but introduces strict identity verification requirements.

For GitLab-based keyless signing, evaluate:

- Whether the CI job can obtain an appropriate OIDC identity token.
- Which issuer and subject/identity claims are presented.
- Whether the signer accepts that issuer and token audience.
- Whether the signing certificate and transparency evidence are verified.
- How identities are constrained to protected projects, refs and trusted runner pools.
- How offline verification and incident recovery work.

**Never** accept any certificate merely because it chains to a known CA; restrict the expected issuer and certificate identity. A generic \`gitlab.example.com\` instance may not be compatible with every public keyless signing service; verify supported issuer configuration before deployment.

## 12. Kubernetes admission enforcement

Signature verification at CI time is valuable but does not by itself prevent later deployment of an unsigned image. Admission controls can enforce trusted artifact policy at the cluster boundary.

Common patterns include:

- Sigstore Policy Controller with compatible trust policies.
- Kyverno image verification rules.
- Other organization-approved admission policy engines.

Illustrative policy requirements:

\`\`\`text
DENY if:
  image is referenced by a mutable tag instead of an approved digest;
  image signature is missing or invalid;
  signer identity is not in the approved trust policy;
  required provenance is missing or untrusted;
  digest is not approved for the target environment.
\`\`\`

Implementation details and support vary by policy engine/version. Validate enforcement using **server-side dry runs and disposable namespaces** before considering production. Do not create a permissive bypass for \`demo-prod\`.

## 13. Multi-cloud operational considerations

| Platform | Signing identity / key storage | Cluster verification |
| --- | --- | --- |
| Amazon EKS | AWS KMS or supported OIDC workflow | Admission controller with trusted signer policy |
| Azure AKS | Azure Key Vault / Managed HSM or workload identity | Admission controller with scoped identity policy |
| Google GKE | Cloud KMS or workload identity federation | Admission policy / approved verification engine |

Cloud workload identity authenticates a job or workload; it does not automatically establish that its image was built by a trusted builder. Keep builder, signer, GitOps automation and runtime workload identities separate.

## 14. Observability and SRE indicators

| Signal | Meaning | Operational action |
| --- | --- | --- |
| Signed-digest coverage | Published artifacts with valid signatures | Block gaps |
| Provenance coverage | Artifacts with verifiable build evidence | Investigate missing attestations |
| Verification failure rate | Signer, registry or policy failures | Triage root cause |
| Signing latency p95 | Release pipeline delay | Inspect signer/KMS availability |
| Untrusted image rejection count | Admission policy effectiveness | Investigate unauthorized deployments |
| Signing identity age/rotation | Key management hygiene | Rotate/revoke as required |
| Transparency availability | External verification dependency | Design fail-closed recovery |
| Registry retention | Ability to retrieve signed rollback digests | Protect known-good artifacts |

Record actual time windows and baselines before assigning SLO targets.

## 15. Troubleshooting runbook

| Symptom | Likely cause | Investigation |
| --- | --- | --- |
| Signing unauthorized | Registry write or attachment permissions | Check repository scope |
| Signature not found | Wrong digest, registry storage or signing mode | Inspect reference and tool version |
| Wrong-key verification fails | Untrusted signer | Confirm public key provenance |
| Attestation verification fails | Predicate type, format, signature or subject | Inspect signed envelope and schema |
| Keyless OIDC rejected | Issuer, audience or identity mismatch | Review approved OIDC claims |
| Admission denies signed image | Wrong signer identity or missing provenance | Compare policy to verified evidence |
| Verification works locally but not in cluster | Trust roots, registry access, policy engine | Compare environment configuration |
| Old digest cannot be pulled | Registry retention or garbage collection | Restore retained artifact |
| CI pipeline hangs during signing | KMS/registry/transparency availability | Inspect external dependencies |
| Signature valid but build untrusted | Weak provenance or compromised builder | Rebuild in trusted isolated environment |

## 16. Incident response and rollback

1. Identify affected digest, signature, signer identity, provenance and deployed environments.
2. Stop promotion of potentially compromised artifacts.
3. Revoke or distrust compromised signing identities in verification policy.
4. Preserve authorized audit logs, signing evidence and registry metadata.
5. Investigate source repository, runner, builder, signing identity and CI configuration.
6. Rebuild from reviewed source in a trusted environment.
7. Generate fresh SBOM, vulnerability report, signature and provenance.
8. Promote the new approved digest through reviewed GitOps changes.
9. If rollback is required, select a **retained** known-good digest signed by a currently trusted identity.
10. Validate Argo CD sync, workload health, security policy and SLOs.

**Key revocation nuance:** Revoking trust may invalidate historical signatures from that signer. Plan emergency signing key rotation and known-good artifact re-attestation without weakening admission controls.
